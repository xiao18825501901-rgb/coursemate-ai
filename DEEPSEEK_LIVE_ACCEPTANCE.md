**Precision about "the run refuses without `--max-cost`" (round-96 correction).** `--max-cost` is
optional in the parser; what is mandatory is a cost policy — `capped` (the default) fails closed
without `--max-cost`, and `owner_authorized_unlimited_for_this_workflow` is the owner's explicit grant
for one workflow. The live runs used the latter, so their artifact records `approved_max_cost: null`
**with** a recorded `conservative_cost_ceiling` and a per-call real cost; that is a permission, not an
absence of accounting.

## 4. Acceptance criteria (and what would fail it)

* Pass: every planned role either completes with the configured alias or fails with a typed error that
  the deterministic fallback handles, and the totals stay inside the ceiling.
* Fail: a role silently falls back to another provider; the observed model differs from the configured
  alias without an explicit configuration change; a refusal is retried; the ceiling is exceeded; a key
  or a raw private payload lands in the evidence file.

**Where that stands:** the runs that were made record **both** outcomes faithfully. Four earlier
canary runs failed and said so (`r81`/`r81b`/`r81c`: `PLAN` `failed`; `r81d`: `EXERCISE_V2` `failed`;
11 calls across the four, each call billed and counted), the two causes were fixed in code rather than
retried away, and the final run has ten roles `completed` on the configured alias, one call each,
inside the ceiling, with no key in the artifact. That is the "no retry, no silent fallback" half of
the criteria **live-proven**; what remains unproven live is the deterministic fallback for a failed
role (the canary aborts instead of falling back) and everything in §7. The canary proves the
integration works against the real API. It does **not** prove teaching quality: for that the artifact
itself says `manual_review_status: REQUIRED`, and **no document in this repository claims the review
happened.**

**The labelled ablation is no longer `NOT_RUN`.** What stood here was *"that requires the labelled
ablation, which is also `NOT_RUN`."* The live A–E ablation has since run with a **live DeepSeek
baseline** (43 answered calls, one per sample, `work/current-change/jev-ablation-live-baseline3.json`)
and returns verdict **`INTERPRETABLE`** — and it is **unfavourable**: citation support 0.667 → 0.833
and the unsupported-claim rate 0.667 → 0.500 improve, while `criterion_error` 0.000 → 0.333 and
`key_fact_retention` 1.000 → 0.000 regress, with `intent_accuracy` tied at 0.667. Populations are 1–8
cases per metric, so this is a small-sample result and is reported as one; the promotion decision it
feeds is still open and nothing has been promoted (`JEV_CALIBRATION_AND_ABLATION_REPORT.md` §9,
`DSH_JEV_DEEPSEEK_EXECUTION_STATE.md` round-91 block).

The naming correction from round 34 stands and is still the reason this table exists: `DEEPSEEK_API_KEY`
is the **canary CLI's** default — `scripts/run_deepseek_canary.py` sets
`DEFAULT_API_KEY_ENV = "DEEPSEEK_API_KEY"` and reads it with `os.environ.get(args.api_key_env)`, so it
is overridable with `--api-key-env` — and **no production service reads that name**. The names the
services actually read, verified in code:

| Service (unit) | Variables | Where it is read |
|---|---|---|
| `rag-api`, V3 teaching path (`coursemate-rag`) | `V3_MODEL`, `V3_MODEL_API_KEY`, `V3_MODEL_BASE_URL` | `app/learning/provider.py` (`settings.v3_model*`) |
| `rag-api`, grounded QA role (same unit) | `DEEPSEEK_CHAT_API_KEY` | `app/config.py::deepseek_chat_api_key` |
| `rag-api`, UI backend API (same unit) | `CMUI_PROVIDER_MODE`, `CMUI_DEEPSEEK_API_KEY` | `app/cm_update/config.py` |
| `agent-api` (`coursemate-agent`) | `AGENT_MODEL_NAME`, `AGENT_MODEL_API_KEY` | `services/agent-api/src/config.ts` |

The failure mode is why this matters: the RAG service's pydantic settings set `extra="ignore"`, so an
unrecognised variable name there is ignored **silently** — no error, no switch. (The `CMUI_*` service is
the opposite: a missing credential there refuses to boot, and those refusals are now pinned by 33 tests.)
The canary itself is run with `--api-key-env` set to whichever variable actually holds the key.

## 6. Production model switch (separate, and gated)

The live site currently answers with **Qwen/Model Studio** (`V3_MODEL=qwen3.8-max`,
`AGENT_MODEL_NAME=qwen3.8-max`, `OPENAI_CHAT_MODEL=qwen3.7-plus`). Rotating the generative path to
DeepSeek happens in the same release window, with its own confirmation, and the rollback path is the
previous release directory plus the pre-migration database backup — never a silent reversion to Qwen.
